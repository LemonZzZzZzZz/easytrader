# 代码审查流程

> 版本：v1.0 ｜ 生效日期：2026-10-17 ｜ 配套文档：《代码审查标准》
> 标准文档回答"审什么"，本文回答"怎么审"。

## 1. 流程总览

```
作者                          系统                    审查者/批准者
 │                            │                          │
 ├─ 拆解任务（小 PR）          │                          │
 ├─ 开发 + 本地自测            │                          │
 ├─ 提交 PR（模板+自检）  ───▶ │                          │
 │                            ├─ CI 门禁（pytest）      │
 │                     ◀── 红 │                          │
 │                  （回作者修，不占用人审）               │
 │                     ─── 绿 ─────────────────────────▶ │
 │                            │              人工审查（24h 内响应）
 │                            │              设计→正确性/安全→测试→细节
 │                            │              意见分级 🔴 / 🟡 / 💭
 │  ◀─── 意见 ────────────────────────────────────────────┤
 ├─ 逐条处置：修复 / 说明理由  │                          │
 ├─ 推送修改 ───────────────▶ │                    ◀── 复审（只审改动+影响面）
 │                            │              有 🔴？── 是 ──▶ 循环
 │                            │                  否
 │                            │              Approve ≥ 1（资金路径 ≥ 2）
 │                            │                    │
 │                     ◀── Squash 合并 ────────────────┘
 ├─ 合并后 24h 观察 + 回滚预案 │
```

## 2. 角色与职责

| 角色 | 职责 |
|------|------|
| 作者 Author | 写自测、写清楚 PR、按分级处置意见、24h 内响应审查意见 |
| 审查者 Reviewer | 24h 内首次响应、按标准清单检查、按四要素格式写意见、复审只看改动与影响面 |
| 批准者 Approver | 维护者/模块负责人；批准合并、裁决 🟡 分歧、在资金路径 PR 上担任第二双眼睛 |

**指派规则**：每个 PR 至少指派 1 名 Reviewer，优先指派熟悉该模块的人（ClientTrader 系 / WebTrader 系 / Followers 系 / miniqmt 系）。无人认领时 @ 当周维护者轮值。

## 3. 标准流程

### 3.1 作者侧

**步骤 1 — 任务拆解**：单个 PR 只做一件事。超过 ~400 行 diff 必须拆分（拆分方法见第 4 节）。

**步骤 2 — 开发与自测**：

```bash
make test                        # pytest -vx --cov=easytrader tests（依赖实盘/网络的用例无环境变量时自动降级）
pipenv run lint                  # pylint 无新增告警
pipenv run format                # black -l 79
pipenv run sort_imports          # isort
pipenv run type_check            # mypy
```

**步骤 3 — 提交 PR**：

- 使用 `.github/PULL_REQUEST_TEMPLATE.md`，自检清单逐项勾选
- 标题语义化：`fix:` / `feat:` / `refactor:` / `perf:` / `docs:` / `test:`
- 关联 issue（`Fixes #123`）
- 在"给审查者的备注"里主动标注：哪里需要重点看、哪里是拍脑袋决定的

### 3.2 审查者侧

**步骤 4 — 自动门禁**：CI 先跑（当前草案为**手动触发**，验证通过后改为提交/PR 自动触发）。**pytest 必须全绿才进人审**；pylint / black / isort 为提示模式（`continue-on-error`，不阻塞合并），存量代码集中清理后转为硬门禁。红的不进人审——机器挑出来的问题不占用人情和上下文。

**步骤 5 — 人工审查（24h 内首次响应）**，按从大到小的顺序，省所有人的时间：

1. **设计与契约**：这个改法对吗？有没有更简单的做法？公开 API 受影响吗？
2. **正确性与安全**：对照《标准》第 5.1 / 5.2 节清单逐项过
3. **测试**：测到点上了吗？能抓住这个 bug 吗？
4. **性能与可维护性**
5. **命名/注释/风格**：放最后，且只提机器管不了的

意见全部用标准格式（四要素 + 分级标记），一轮给全。

**步骤 6 — 修改与复审**：

- 作者逐条回复：已修复 / 说明理由 / 提问
- 复审只关注"改动 + 影响面"，不重新开火、不翻旧账
- 每轮复审 24h 内完成

### 3.3 合并

**步骤 7 — 合并与观察**：

- Squash merge，commit message 写清动机（写给 6 个月后的自己）
- 合并后 24h 内关注线上表现：远端服务日志、用户 issue、成交异常
- 高危变更提前写好回滚预案："如果出事怎么退"

## 4. PR 大小与拆分策略

- 目标 **< 400 行 diff**；> 800 行时审查质量必然下降，必须拆
- 拆分方法：
  1. **纵向拆**：先搭骨架（接口 + 空实现 + 测试）一个 PR，再逐个填实现；
  2. **横向拆**：机械重构（改名、移动文件）一个 PR，逻辑变更另一个 PR；
  3. **依赖拆**：底层库先行，上层跟随。
- 确实拆不了的（如一次性数据迁移）：在 PR 中说明理由，并约定审查方式（如组织一次集中评审会）。

## 5. SLA 与升级机制

| 环节 | 时限 | 超时升级链 |
|------|------|------------|
| 首次审查响应 | 24h（工作日） | 私信提醒 → 群内 @ → 换人 |
| 意见修改 | 24h | 说明阻塞原因，否则 PR 挂起 |
| 复审 | 24h | 同升级链 |
| 紧急阻塞（关联线上事故） | 2h | 直接同步，不等 |

假期与高峰期提前在团队日历标注，Reviewer 明确交接。

## 6. 紧急修复（Hotfix）流程

线上事故（错误下单、登录失效、服务崩溃）允许绿色通道：

1. 从 `main` 切 `hotfix/*` 分支，至少 2 人知情；
2. 修复 + 最小化验证（**能复现问题的那条路径必须验证**）；
3. 维护者 IM 批准后合并；
4. **48 小时内补齐正式 PR 审查**（回溯审查），补齐测试与文档；
5. 事故记录进 issue，双周复盘。

绿色通道是**债务不是福利**：每次 hotfix 必须在复盘里回答"为什么没走到正常流程"。

## 7. 度量与持续改进

双周从 GitHub 抓取以下指标：

| 指标 | 说明 | 目标 |
|------|------|------|
| PR 周期时间 | 开启→合并的中位耗时 | 逐月下降 |
| 一次通过率 | 无修改直接合并的占比 | 逐步上升 |
| 24h 响应达标率 | 首次响应 < 24h 的占比 | > 90% |
| 缺陷逃逸率 | 合并后发现的问题数 / 合并 PR 数 | 逐月下降 |
| 🔴 意见分类 | 哪类问题反复出现 | 决定加 lint 规则还是补文档 |

双周复盘 30 分钟：只看数据和典型案例，不批斗。反复出现的 🔴 类别，优先用工具消灭（pylint 规则、CI 检查、模板勾选项）。

## 8. 工具链

| 工具 | 用途 | 状态 |
|------|------|------|
| black -l 79 / isort | 格式与导入排序 | 已有，PR 前必跑 |
| pylint（.pylintrc） | 静态检查 | 已有，CI 提示模式接入 |
| mypy | 类型检查 | 已有（宽松），逐步收紧 |
| pytest（make test） | 测试 | 已有，CI 硬门禁接入 |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 模板 | 本次新增 |
| `.github/workflows/ci.yml` | CI 门禁 | 本次新增（**草案，默认仅手动触发**）：官方 PyPI HTTPS 安装、固定 `pip<24.1` 与检查工具版本，pytest 硬门禁 + pylint / black / isort 提示模式 |
| pre-commit（可选） | 本地提交钩子 | 建议后续接入 |

> **CI 草案的 Python 版本依据（2026-10-18 对 pypi.org 实测，win_amd64）**：
> - `lxml==4.2.3` 仅有 cp36 wheel，3.7 无 wheel——这是选定 3.6 的决定性因素；
> - `pandas==0.23.3` 有 cp36/cp37 wheel，无 cp38+；
> - `numpy==1.15.0`、`Pillow==5.2.0` 有 cp36/cp37 wheel；
> - 另有一个与 Python 版本无关的硬约束：`pandas==0.23.3` 的旧版元数据无法被 pip>=24.1 解析（报错提示 `Please use pip<24.1`），CI 中已固定 `pip<24.1`。
> 若 runner 清单下架 3.6：**不能简单降到 3.7/3.8**（lxml 3.7、pandas 3.8+ 均无 wheel），只能走"升级依赖钉版"路线。
>
> **手动触发的分支限制（2026-10-18 第三轮复审补充）**：`workflow_dispatch` 只能触发默认分支（master）上的 workflow。本文件当前在 `fix/ths-gui-fixes` 分支，仅推送该分支不会出现在 Actions 页面的 Run workflow 列表中。runner 验证二选一：① 先合入 master 再到 Actions → CI → Run workflow；② 暂不合并时把 `on` 临时改为 `[workflow_dispatch, pull_request]`，开一次 PR 验证后改回 `[workflow_dispatch]` 再合入。两种路径的详细说明已写入 `ci.yml` 文件头注释。

## 9. 落地路线图

| 阶段 | 时间 | 动作 |
|------|------|------|
| 试点 | 第 1–2 周 | 全员过一遍两份文档；挑 2–3 个进行中的需求按新流程走；PR 模板上线，CI 手动触发试运行 |
| 推广 | 第 3–4 周 | 全部新 PR 按流程执行；收集"不爽的点" |
| 固化 | 第 5 周起 | 依据反馈修订文档到 v1.1；纳入新人 onboarding；指标上墙 |

## 10. 反模式（不要这么干）

- ❌ **风格圣战**：在审查里吵 black 能解决的事
- ❌ **抠字眼**：把 💭 当 🔴 用，透支意见的可信度
- ❌ **代写代码**：审查者直接 push 到作者分支（除非作者明确请求）
- ❌ **拖字诀**：攒一堆意见一次爆发，作者的上下文早就丢了
- ❌ **只点赞**：无脑 LGTM，出了事一起背
- ❌ **审旧账**：复审时翻上一轮已解决的问题
