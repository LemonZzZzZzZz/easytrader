# 代码审查标准

> 版本：v1.0 ｜ 生效日期：2026-10-17 ｜ 配套文档：《代码审查流程》
> 本文件是"审什么"的判定标准，流程文档是"怎么审"的操作规程，两者配合使用。

## 1. 目的

代码审查不是为了"把关"，而是为了三件事：

1. **在合并前发现缺陷**——尤其是资金路径（下单/撤单/资金查询）上的缺陷，这类缺陷的代价是真金白银；
2. **让知识流动**——作者教审查者上下文，审查者教作者经验，双向教学；
3. **保持长期可维护**——今天的妥协就是明天的维护成本。

## 2. 适用范围

- 所有以 Pull Request 合入 `main` 的代码变更；
- 紧急热修复走例外流程，见《代码审查流程》第 6 节；
- 文档、配置、CI 变更同样要审——配置错误同样是生产事故源。

## 3. 基本原则

1. **一次给全反馈**：不要挤牙膏式逐条提意见，一轮审查尽量给全，节省双方的上下文切换成本。
2. **先架构后细节**：先看设计和正确性，最后看命名和风格。风格问题交给工具（black/isort/pylint），不占用人脑。
3. **对事不对人**：评论指向代码，不指向人。
4. **不懂就问**：意图不明时提问，而不是假设它是错的。
5. **看到好代码要点赞**：审查是双向的，别只挑刺。
6. **机器能做的不要人做**：测试由 pytest 在 CI 硬门禁；格式（black）、导入顺序（isort）、坏味道（pylint）由 CI 以提示模式先行，存量代码完成一次集中清理后转为硬门禁。人只审机器审不了的——设计、正确性、安全、可维护性。

## 4. 意见分级与处置规则

| 级别 | 标记 | 定义 | 处置方式 |
|------|------|------|----------|
| 阻塞 | 🔴 | 正确性、安全、数据风险，不修不能合 | **必须修复**，修复后复审 |
| 建议 | 🟡 | 应该改进，但可以合理解释后保留 | 修复，或在 PR 中书面说明理由，由审查者/Approver 裁决 |
| Nit | 💭 | 可选改进，吹毛求疵级 | 作者自行决定，不强制 |

**裁决规则**：🟡 意见出现分歧时由 Approver 裁定；仍无法达成一致，按"可逆性"决策——容易回滚的听作者的，难回滚的（资金路径、协议变更、数据迁移）听审查者的。

**分级反模式**：把 💭 当 🔴 用。三次之后没人认真看你的意见。

## 5. 审查维度与检查清单

### 5.1 正确性（权重最高）

- [ ] 分支是否覆盖所有情况？else/except 分支是"真的想了"还是"凑数"？
- [ ] 边界条件：空列表 / None / 0 / 负数 / 极大值 / 字符串编码
- [ ] 错误处理：`except` 之后是恢复、上报，还是吞掉？
- [ ] **幂等性**：重复点击/重复调用会发生什么？交易系统重复下单 = 真实亏损，这是本项目最典型的事故形态
- [ ] 状态一致性：GUI 弹窗处理中途失败后，客户端处于什么状态？下次启动能否恢复？
- [ ] 时序：固定 `sleep` 等待 vs 轮询带超时；后台心跳线程与主线程的共享状态

### 5.2 安全（红线，一票否决）

- [ ] **凭据零容忍**：账号、密码、token、cookie 不得进仓库。`account.json`、`account.session`、`secrets/` 等已在 `.gitignore`，新增同类文件必须同步加入
- [ ] **日志脱敏**：logger 输出不得包含资金账号、密码、完整 cookie/token；`server.py` 的 Flask 访问日志同理
- [ ] **资金路径**：`buy` / `sell` / `cancel_entrust` 及资金查询（`balance` / `position` / `today_entrusts`），必须做**双向校验**——入口校验参数（价格、数量、代码合法性），出口校验结果（成交回报 vs 委托回报，不能把"已报单"当"已成交"）
- [ ] **第三方请求**：所有 `requests` 调用必须有 `timeout`；重试必须有次数上限；对雪球等有限频的接口要考虑请求间隔
- [ ] **远端接口注入面**：`server.py` 暴露的 HTTP 接口要校验输入（代码、数量、价格），防止非法参数驱动交易客户端乱点

### 5.3 性能

- [ ] GUI 自动化中是否有"固定 sleep 等待"？能用带超时的 wait/poll 就不要死等
- [ ] 是否重复解析同一份数据（BeautifulSoup/lxml 大文档多次解析）？
- [ ] 热路径上的 I/O 是否必要？关键路径是否用 `@perf_clock`（`utils/perf.py`）覆盖？
- [ ] 网络请求能否合并、缓存或降低频率？

### 5.4 可维护性

- [ ] 命名是否自解释？避免无意义缩写
- [ ] 函数是否超过 ~50 行或 3 层以上缩进？圈复杂度是否过高？
- [ ] 是否有复制粘贴的重复代码？`grid_strategies.py` / `refresh_strategies.py` 的解析逻辑是高发区，相似度高的应提取
- [ ] 注释是否解释"为什么"而不是复述"是什么"？
- [ ] 异常是否使用项目异常体系（`TradeError` / `NotLoginError` / `TradeVerificationError`），而不是裸 `raise Exception`？
- [ ] 日志是否使用共享 logger（`logging.getLogger("easytrader")`），而不是自建模块级 logger 或 `print`？

### 5.5 测试

- [ ] 新功能/行为变更是否带测试？修 bug 是否带回归测试？
- [ ] 测试是否隔离外部依赖（mock `requests` / pywinauto），不连真实券商？
- [ ] 依赖券商实盘/网络的测试是否有门控，无环境变量时自动降级或跳过？（现有范例：`test_xq_follower.py` 的 `EZ_TEST_XQ_COOKIES`；`copilot-instructions.md` 约定的 `EZ_TEST_CLIENTS` 尚未在测试中落地，新增此类测试必须带上）
- [ ] 测试是否稳定（无顺序依赖、无裸露 sleep）？

### 5.6 兼容性

- [ ] 公开 API（`use()` / `follower()` / `ClientTrader` 子类的公开方法）是否保持向后兼容？破坏性变更需在 PR 描述中显著说明
- [ ] 依赖版本变更是否评估了影响？**`pywinauto==0.6.6` 是钉死的，升级前必须实测**
- [ ] 平台适配代码是否正确门控？Windows-only 模块（pywinauto/ctypes）不得导致 macOS/Linux 导入崩溃
- [ ] `xtquant` 等专有 SDK 不得成为测试环境的硬依赖

## 6. Python 专项规则

多数可由 pylint/mypy 兜底，审查时重点看"工具漏网的"：

1. 禁止裸 `except:`，禁止 `except Exception: pass`（吞异常）
2. 禁止可变默认参数（`def f(x=[])`）
3. 文件/网络资源用 `with` 管理或确保关闭
4. 新代码（尤其 `miniqmt/`）写 type hints；老代码与周边风格保持一致，不为加类型而加类型
5. 字符串格式化用 f-string（与现有代码一致）
6. 循环内不做无意义重复计算；大集合用生成器
7. 注释、错误信息、日志一律中文（项目约定，见 `.github/copilot-instructions.md`）

## 7. 审查意见书写格式

每条意见必须包含**位置 + 问题 + 为什么 + 建议**四要素：

```
🔴 **正确性：重复下单风险**（示例，非真实缺陷）
`clienttrader.py` L726 `buy()`：假设弹窗确认失败后直接返回 False，但委托实际已提交。

**Why**：GUI 点击与委托提交之间存在时序窗口，返回 False 会让调用方误以为未委托，
重试即造成重复下单，产生真实资金损失。

**Suggestion**：
- 失败时先调用 `today_entrusts()` 确认委托状态，再决定是否重试
- 可参考 `TradeVerificationError` 的既有处理方式
```

规则：能贴代码/行号就不描述；建议给方向，不代写整段代码。

## 8. 审查通过标准（合并门槛）

- [ ] CI 的 pytest 全绿（硬门禁）；pylint / black / isort 检查为提示模式，不阻塞合并，存量代码集中清理完成后转为硬门禁
- [ ] 无未解决的 🔴 意见
- [ ] 所有 🟡 意见已修复或有书面理由
- [ ] 至少 1 名 Approver 批准；**涉及资金路径的 PR 需 2 人批准**
- [ ] PR 描述完整：类型、动机、测试、风险、回滚

## 9. 作者自检清单

提交 PR 前逐项过一遍（已内置于 `.github/PULL_REQUEST_TEMPLATE.md`），核心几条：

- 本地 `make test` 全绿；`lint` / `format` / `type_check` 无新增告警
- 新行为/修复已补测试，无法测试的写明原因
- 无凭据/账号信息入库，日志无敏感信息
- 资金路径已做双向校验
- PR 控制在 ~400 行内，拆不了的写明理由
